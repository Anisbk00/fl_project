CHECKOUT ATTEMPT AND CONCURRENCY PROTOCOL

Create Checkout through a recoverable saga. Do not hold a database transaction open while calling Stripe.

Required sequence:

1. Receive a same-origin POST or Server Action containing only the current cart version and current versioned-consent acknowledgement identifiers—not prices or Stripe identifiers.
2. Apply durable rate limits using the cart-token digest and a privacy-preserving IP/device key where practical. Do not use an in-memory Map and claim it provides distributed protection.
3. Transactionally lock and read the cart.
4. Re-resolve every item from trusted product, rights, and asset tables.
5. Enforce every purchase gate.
6. Reject empty, free-only, stale, mixed-currency, excessive, or changed carts with a refreshed typed cart response instead of silently charging a different total.
7. Validate that required consent evidence is current and bound to this exact cart fingerprint.
8. Build a deterministic server-side cart fingerprint from sorted trusted product, version, price, currency, asset, license, and policy facts.
9. Reuse an existing unexpired open Checkout Session only if its fingerprint and consent versions match exactly.
10. Otherwise, create one immutable `creating` checkout attempt and its item snapshots under a unique database constraint.
11. Commit the database transaction.
12. Create the Stripe Checkout Session using the attempt’s stable non-PII idempotency key and exact immutable attempt data.
13. Persist the returned Session ID, PaymentIntent when available, URL, and expiry.
14. Transition the attempt to open.
15. Never return the full Stripe secret response object to the browser.
16. Redirect server-side to the exact Stripe-hosted Session URL or return only a narrowly validated Stripe redirect URL.

Double-clicks, simultaneous tabs, Vercel retries, client retries, and timeouts after Stripe accepted the request must converge on the same attempt and Session.

Use both:

- Database uniqueness and locking.
- A Stripe idempotency key derived from the random checkout-attempt ID.

Never use email or other PII as an idempotency key.

Never create a new idempotency key when retrying the same attempt.

Never automatically create a second attempt after an ambiguous Stripe error. Mark it for reconciliation.

If Stripe creation succeeds but the local update fails, retry with the same idempotency key to recover and persist the same Session response.

If Stripe returns a persistent ambiguous or 5xx idempotent response, do not create another charge path blindly. Surface a safe reconciliation state with a correlation ID.

- Retrieve all Checkout line items when needed and handle pagination.
- Do not use the Stripe event `created` timestamp for duplication or ordering decisions.
- Make every state application repeatable and concurrency-safe.
- Treat a second distinct Stripe event object concerning the same resource as a valid update or no-op based on authoritative current state.
- Use monotonic transitions so older failure or processing events cannot regress a paid or refunded order.
- Keep network calls outside long-held database locks.
- Apply verified results through short compare-and-set transactions.
- Preserve only redacted failure codes and correlation IDs.
- Never store secrets in processor errors.
- Purge or null complete private event payloads after a documented short retention period once durable business fields exist.
- Retain the event envelope and processing audit required for reconciliation.

Stripe event retrieval is time-limited, so local durable receipt and prompt reconciliation are mandatory.

Add an authenticated administrator/operator reconciliation action or server-only script plus a scheduled scan for:

- Stuck inbox rows.
- Checkout attempts left in creating/open states too long.
- Stripe Sessions missing after local update failure.
- Pending payments.
- Paid Stripe Sessions without a local order.
- Pending refunds.
- Dead-letter events.

Reconciliation must retrieve Stripe’s current state and invoke the same idempotent state-transition functions. It must never directly set `paid = true`.

PAYMENT AND ORDER STATE MACHINE

Keep Checkout attempt, payment, refund, dispute/hold, and fulfillment states separate. Do not use one overloaded Boolean.

Support at least these semantics:

- Session created/open:
  - Visitor may pay.
  - No order entitlement exists.

- Session completed but payment status unpaid or processing:
  - Create or update a pending order or attempt as appropriate.
  - Store email and financial totals safely.
  - Do not mark paid.
  - Do not produce a future fulfillment trigger yet.

- Immediate completed Session with freshly retrieved `payment_status = paid`:
  - Atomically upsert exactly one paid order and immutable items.

- `checkout.session.async_payment_succeeded`:
  - Retrieve the current Session.
  - Perform the same idempotent paid transition only if its payment status is actually paid.

- `checkout.session.async_payment_failed`:
  - Mark the attempt or order payment failed.
  - Preserve its history.
  - Create no entitlement.
  - Allow a new reviewed Checkout attempt from the cart.

- `checkout.session.expired`:
  - Expire the attempt.
  - Preserve or reopen the unpaid cart safely.
  - Never create an entitlement.

- Refund events:
  - Reconcile individual refunds and aggregate refunded amount with Stripe.
  - Represent pending, succeeded, failed, partial, and full outcomes accurately.

- Dispute created:
  - Put the order into a future-fulfillment hold or review state.
  - Keep dispute state separate from refund state.

The paid transition must execute in one database transaction and:

1. Lock and reread the checkout attempt or order.
2. Match the opaque attempt reference.
3. Match Stripe Session ID.
4. Match expected test/live environment.
5. Match currency.
6. Match expected subtotal and Stripe totals.
7. Match Stripe line items.
8. Match PaymentIntent.
9. Verify that the Session is genuinely paid rather than merely complete.
10. Verify that a customer delivery email exists.
11. Detect mismatched amount, currency, item set, rights recall, unavailable asset, or invalid metadata.
12. Route unsafe or mismatched payments into a visible `manual_review` or fulfillment-hold state instead of issuing access.
13. Upsert exactly one order under unique attempt and Session identifiers.
14. Insert immutable order-item snapshots from the trusted checkout attempt.
15. Include purchased deliverable asset-version and policy/license references.
16. Record Stripe totals, identifiers, and authoritative payment time.
17. Mark the cart converted.
18. Mark the checkout attempt completed.
19. Write safe audit and state-transition events.
20. Expose one documented transactional extension point where Step 6 can atomically create download grants and a delivery-outbox job before commit.

Do not call an email provider, issue a token, sign a Storage URL, or attach a package during Step 5.

Set fulfillment explicitly to `not_started` or `blocked_until_step_6` so payment cannot be mistaken for completed delivery.

Product-price changes after Session creation must not rewrite its immutable attempt or order snapshot. Honor the exact valid short-lived Checkout snapshot if payment succeeds.

If a product is normally unpublished after Session creation but its purchased asset version and distribution rights remain valid, follow the documented sale policy.

If rights were revoked, the asset became quarantined, or fulfillment became unsafe before payment completed:

- Record the authoritative payment.
- Put the order into manual review or automatic-refund consideration.
- Never silently substitute another file.
