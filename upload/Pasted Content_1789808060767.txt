Music Project Store — Master Plan and Implementation Prompts

Canonical project reference — created 18 September 2026; updated 19 September 2026

1. Product vision and non-negotiable requirements

Build a worldwide digital-product store for music producers, inspired by the useful parts of FLPStudio.com's business model but not copied visually or technically.

The store will sell only content that the owner has the legal right to distribute, including:

original DAW project files and educational remakes;

original stems rendered by the owner;

original WAV/sample packs comparable in format and usefulness to well-known producer packs, but containing no copied third-party audio, branding, artwork, or files;

optional free products used as acquisition products.

Core user requirements:

Public storefront with no customer registration or customer login.

Guest cart and guest checkout.

Only the owner/admin can sign in.

Admin can create, edit, archive, publish, and organize products and upload assets.

Every product can have an audio preview and optional video preview.

Every product page exposes useful technical information: product type, DAW and version, BPM, musical key, duration, included formats/files, total download size, required plugins and versions, genre, license summary, and update date.

Payments use Stripe-hosted Checkout, with eligible major payment methods and wallets managed dynamically in Stripe. The application never handles card details.

As soon as Stripe authoritatively confirms an immediate or delayed payment, the buyer automatically receives the package-access email without admin intervention. The production target is delivery within 60 seconds of confirmation under normal conditions, backed by idempotency, retries, and reconciliation.

Paid deliverables are private and are never exposed by permanent public URLs.

Supabase is the database, authentication, and object-storage platform.

Vercel is the deployment platform.

The finished product must be secure, fast, accessible, SEO-ready, observable, tested, and release-ready.

2. Lessons carried forward from the FLP Studio audit

The new product must deliberately improve on the weaknesses found in the reference store:

Do not allow broken home-page redirects or dead collection links.

Make a large catalog discoverable with filters for genre, BPM, musical key, DAW/version, plugins, product type, price, and recency.

Use clean product names and readable cards; never truncate the only useful identifying information.

Display compatibility information before purchase.

Add verified-buyer reviews later; never fabricate reviews or structured review data.

Use one semantic H1 per page and valid Product, Offer, BreadcrumbList, and eligible Review structured data.

Avoid keyword stuffing and auto-generated low-quality product copy.

Render money accessibly and consistently from integer minor units.

Keep refund, license, privacy, consumer-rights, and download policies consistent.

Clearly state independence from DAW vendors and referenced artists whenever legally appropriate.

Add measurement for search, preview play, add-to-cart, checkout start, purchase, and download without leaking sensitive data.

Prefer improving discovery and trust over blindly adding thousands of products.

3. Architecture decisions

Application

Next.js 16 App Router, latest stable 16.x release at implementation time; no canary or beta framework packages.

React and TypeScript versions selected by the stable Next.js release.

Node.js 24.x, pinned in package.json and local tooling because it is Vercel's current default LTS runtime.

pnpm with a committed lockfile and pinned package-manager version.

TypeScript strict mode, including noUncheckedIndexedAccess.

Tailwind CSS and shadcn/ui for the later visual-system phase; install only what Step 1 actually uses.

Server Components by default. Client Components only for interactivity such as the audio player, filters, cart, and admin upload progress.

No custom Express server. Use Server Actions for authenticated mutations and Route Handlers for webhooks, checkout creation, downloads, and other true HTTP endpoints.

Every Server Action and Route Handler performs its own authentication, authorization, input validation, and rate-limit check where applicable. A protected layout or Next.js Proxy is never treated as the only authorization layer.

Supabase

Postgres is the source of truth for catalog metadata, orders, fulfillment state, and download grants.

Supabase Auth is used only for manually provisioned admin accounts. Public self-sign-up is disabled.

Admin authorization is based on the authenticated Supabase user ID appearing in a private admin allow-list, not merely an email supplied by the browser.

Require TOTP MFA/AAL2 for admin access before production launch.

Use current sb_publishable_... and sb_secret_... API keys. Do not build a new project around the legacy anon or service_role keys.

The publishable key may be used in the browser because RLS is the real access boundary.

The secret key is imported only from server-only modules and never appears in a client bundle, log, URL, repository, or public document.

Enable RLS and explicit grants on every table in an exposed schema. Test allow and deny cases with pgTAP/Supabase database tests.

Public visitors can read only published, rights-cleared catalog data and its explicitly public media.

Public previews and cover images live in an intentionally public bucket for CDN delivery.

Purchased archives/project files live in a private bucket. Later, a server-side fulfillment check will issue short-lived signed download URLs.

Large admin uploads go directly from the authenticated admin browser to Supabase Storage using TUS/resumable uploads or signed upload tokens. Never proxy large ZIP/WAV/project files through Vercel Functions.

Use immutable/versioned storage paths rather than overwriting the same CDN path.

Payments and fulfillment — later phase

Stripe-hosted Checkout, guest checkout, one-time payments.

The server recalculates every line item from trusted database values; it never accepts price or entitlement data from the browser.

Let Stripe dynamically present eligible payment methods configured for the merchant, currency, amount, and customer location. Do not promise that every method is available in every country.

Stripe webhooks are the payment authority. The success page is for user experience, not proof of payment.

Verify Stripe signatures against the raw request body.

Make fulfillment idempotent and concurrency-safe using unique Stripe event/session/payment identifiers and database transactions.

Handle both immediate success and delayed payment events before granting files.

The browser success redirect must never trigger delivery. A verified paid webhook creates the entitlement and a durable email-delivery job atomically, then an idempotent worker attempts delivery immediately and retries transient failures.

Use Stripe Tax or another reviewed tax solution only after merchant country, legal entity, and tax obligations are confirmed.

Guest delivery — later phase

Collect the customer's delivery email through Stripe Checkout.

After verified payment, create an order, immutable order-item snapshots, and download grants.

Automatically email a high-entropy package-access link immediately after confirmed payment. Store only a cryptographic hash of the access token in the database.

The email is the delivery channel, but large ZIP, WAV, stem, and project packages are not attached to it. The email links to a secure access page that issues short-lived private-storage URLs after validation.

Use a durable transactional outbox/job record, provider idempotency where available, exponential retry with a bounded schedule, failure visibility, and a reconciliation/resend path so a temporary email-provider failure cannot silently lose a paid delivery.

Validate token status, order payment status, expiry, revocation, and download limits before issuing a short-lived Supabase signed URL.

Do not expose storage object paths in public catalog APIs.

Be honest that signed links reduce casual unauthorized sharing but cannot provide perfect DRM after a customer downloads a file.

Performance

Render public catalog/product content on the server and cache/revalidate deliberately.

Keep admin and order pages dynamic and uncached.

Use optimized images, compressed preview audio, lazy loading, and small client bundles.

Use URL search parameters for shareable catalog filters.

Add indexes that match real catalog queries; confirm with query plans instead of guessing.

Place Vercel Functions near the selected Supabase project region.

Define measurable launch budgets later for Core Web Vitals, JavaScript weight, images, and audio.

Security model

Defend specifically against:

unauthorized admin access and privilege escalation;

public reads of drafts or private deliverables;

secret-key exposure;

price/cart manipulation;

forged or replayed payment webhooks;

duplicate fulfillment;

guessing, replaying, or sharing download links;

XSS through product descriptions and metadata;

malicious or invalid uploads;

abusive checkout/download/API traffic;

sensitive customer/payment data appearing in logs;

dependency and supply-chain vulnerabilities.

Important controls include admin MFA, server-side authorization, RLS and grants, private storage, signed URLs, input schemas, sanitization, safe Markdown rather than arbitrary HTML, file allow-lists and size limits, checksums, rate limits, CSP/security headers, idempotency constraints, minimal data retention, dependency updates, audit logs, and tested backups.

4. Phased implementation roadmap

Step 1 — Foundation, architecture, and secure catalog data layer

Create the repository, pinned toolchain, domain-oriented folder structure, environment validation, Supabase local configuration, catalog schema, storage buckets, RLS/grants, database security tests, CI, and architecture/security documentation. No production storefront, admin CMS, cart, or payment implementation yet.

Step 2 — Brand system and responsive storefront shell

Establish the original visual direction, responsive navigation, home-page information architecture, footer/trust navigation, accessible component primitives, loading/error/empty states, and performance budgets. Do not copy FLP Studio's design.

Step 3 — Catalog, product pages, filters, SEO, and audio previews

Build real data-backed catalog/product pages, fast URL-based filters, search, sorting, native performant preview playback, compatibility panels, related products, metadata, canonical URLs, sitemap, robots rules, Open Graph, and validated structured data.

Step 4 — Admin authentication and product CMS

Implement manually provisioned admin login, disabled public sign-up, MFA/AAL2 enforcement, protected server actions, product CRUD, draft/preview/publish workflow, rights-clearance gate, genres/plugins management, direct resumable uploads, validation, checksums, versioned assets, audit history, and safe delete/archive behavior.

Step 5 — Cart and Stripe guest checkout

Implement a durable guest cart, trusted server-side price lookup, checkout-session creation, dynamic eligible payment methods, customer email collection, terms/consumer consent where legally required, tax configuration, success/cancel flows, signature-verified webhooks, idempotent orders, refunds, and exhaustive test-mode scenarios.

Step 6 — Secure digital fulfillment

Implement private deliverables, order-item snapshots, hashed download tokens, and automatic package-access email delivery immediately after webhook-confirmed payment, targeting under 60 seconds in normal conditions. Use a durable outbox/job, idempotent sends, retries, failure monitoring, short-lived signed URLs, expiry/revocation/download limits, delayed-payment handling, refund revocation rules, resend/recovery without customer accounts, and fulfillment reconciliation.

Step 7 — Trust, legal pages, reviews, and growth features

Add consistent terms, privacy/cookie, refund, license, copyright/takedown, compatibility, and contact information reviewed for the operating jurisdiction. Add verified-purchase reviews, free-product/email funnel, bundles, promotions, recommendations, and trust content without dark patterns.

Step 8 — Observability, security, performance, and accessibility hardening

Add privacy-aware analytics, error monitoring, structured redacted logs, alerts, rate limits, bot controls, security headers/CSP, dependency/secret scanning, RLS regression tests, webhook/download abuse tests, WCAG review, browser/device E2E coverage, load checks, query analysis, Lighthouse/Core Web Vitals validation, backup/restore drill, and incident runbooks.

Step 9 — Vercel production deployment and release

Create separate development/preview/production configuration, provision production Supabase/Stripe/email services, rotate and scope secrets, set matching regions, configure domain/DNS/TLS, validate webhook endpoints, run migrations safely, seed the real admin, complete merchant/legal/tax checks, execute a release checklist and rollback test, perform a real low-value purchase/refund/download test, and launch with monitoring.

5. Legal and operational release gate

The store must not publish or sell:

stems extracted from commercial masters;

third-party sample-pack files, presets, MIDI, artwork, or project assets without redistribution rights;

a famous song remake merely because it was recreated by ear, unless the composition, included audio/assets, naming, artwork, and intended distribution have been reviewed and cleared as required;

product copy or branding that implies endorsement by an artist, label, DAW vendor, or sample-pack creator.

The database therefore includes a rights status and prevents publication until a product is marked original or licensed. This is an engineering guardrail, not a substitute for legal advice. Before accepting live orders, verify business-registration, payment-processor eligibility, tax/VAT, consumer-contract, privacy, copyright, trademark, licensing, refund, and digital-withdrawal requirements for the actual operating jurisdiction and target markets.

Authorization, grants, and RLS

Treat RLS and SQL grants as one design. Enable RLS on every table in an exposed schema, revoke broad defaults, and grant back only required operations.

Use a carefully written SECURITY DEFINER admin-check function with an empty/fixed search_path, least privilege, and explicit execute grants. Admin status must be determined from auth.uid() and the private allow-list. Do not trust an email, request field, or client claim as admin authorization.

Required access matrix:

anonymous/public visitor: may select only published, rights-cleared products and their public taxonomy/requirements/media;

anonymous/public visitor: cannot see draft/archived/rejected/unreviewed products, private deliverable rows, admin identities, or private paths;

anonymous/public visitor: cannot insert, update, or delete anything;

authenticated non-admin: gains no mutation powers and cannot see private deliverables or admin data;

authenticated allow-listed admin: can perform the catalog-management operations needed by the later CMS;

privileged secret-key server client: reserved for narrowly reviewed server-only operations and never used to compensate for broken RLS.

Write separate policies per operation rather than one opaque FOR ALL policy. Ensure joins cannot leak unpublished product relationships.

   - Add `Product` fields that are visible and truthful. Include `Offer`/merchant properties only when commerce is genuinely enabled and the page can actually be purchased; Step 3 must not falsely advertise availability or checkout capability.
   - Never include fabricated `Review`, `AggregateRating`, brand, SKU, inventory, shipping, or return information.
   - Ensure price/currency in structured data, when enabled later, comes from the same trusted fields rendered on the page.
   - Validate representative output with automated schema tests and, where accessible, Google's Rich Results Test or Schema Markup Validator. Record what was and was not externally validated.

5. Content quality
   - One meaningful H1 per page, logical headings, descriptive link text, real alt text for meaningful covers, empty alt for decorative motifs, and no keyword stuffing.
   - Category/filter labels should help buyers choose rather than create thin SEO doorway content.

Security requirements

- Maintain every Step 1 RLS/grant denial and add regression tests for new functions/views.
- No public code path may import the secret Supabase client.
- Parameterize database input; never interpolate search/filter/sort input into SQL.
- Use allow-listed sort keys mapped to known SQL expressions. A URL value must never become an identifier or order clause directly.
- Safe Markdown/plain text only; no arbitrary stored HTML and no unsanitized `dangerouslySetInnerHTML` except the separately sanitized JSON-LD serialization.
- Validate public media kinds and expected public bucket/path format before rendering URLs.
- Do not proxy whole preview files through a Vercel Function.
- Avoid exposing stack traces or database details in user-visible error states.
- Run dependency and secret scans already configured by Step 1 and inspect production client bundles for server-only leakage.

Performance and accessibility

- Keep catalog and product content server-rendered and meaningful without waiting for hydration.
- Constrain client code to filter enhancement, mobile filter UI, and audio controls.
- Paginate; never load the whole catalog or all relations into one request.
- Fetch only card fields for lists and full fields only for one product page.
- Use optimized responsive covers with accurate `sizes`, stable dimensions, and no layout shift.
- Avoid eager-loading below-the-fold covers and all audio. Prioritize only genuine LCP media.
- Preserve the Step 2 Lighthouse targets: at least 90 Performance, 95 Accessibility, 95 Best Practices, and 90 SEO for representative production-mode routes where the environment supports measurement.
- Preserve eventual field targets of LCP <= 2.5s, INP <= 200ms, and CLS <= 0.1 at the 75th percentile.
- Test at 320, 375, 768, 1024, 1440, and 1920 CSS pixels with no unintended overflow, clipped filter UI, unusable player, or layout collision.
- Automated accessibility scans on catalog, filtered/empty states, product detail, mobile filters, and the audio player must have no serious or critical violations.
