STEP 9 — VERCEL PRODUCTION DEPLOYMENT AND RELEASE

You are a senior full-stack, application-security, site-reliability, payments, database, email-deliverability, and release engineer. Implement Step 9 only for the existing production-grade digital music-product store.

Read the complete repository, project instructions, migrations, generated types, tests, architecture decisions, legal-release gates, threat model, restore evidence, incident runbooks, and Steps 1–8 documentation before changing anything.

Preserve all working behavior. Do not invent credentials, business or legal facts, DNS ownership, merchant approvals, provider configuration, purchases, refunds, test results, deliverability evidence, monitoring coverage, or launch status.

CURRENT ARCHITECTURE

The application uses:

- Next.js App Router with strict TypeScript;
- Supabase Postgres, Auth, and Storage;
- Stripe-hosted one-time guest Checkout;
- Resend behind a provider-neutral transactional-email boundary;
- Vercel;
- manually provisioned administrators protected by TOTP MFA/AAL2;
- no buyer accounts, login, profile, or customer library;
- private deliverables separated from public previews;
- Stripe webhooks as payment authority;
- durable fulfillment and email outbox processing;
- immutable order-item and deliverable snapshots;
- secure fragment-based package-access links;
- private Supabase Storage with short-lived signed URLs.

Confirmed payments must atomically create immutable entitlements and durable fulfillment email work, normally targeting email-provider acceptance within 60 seconds.

Step 7 added legal/trust gates, reviews, free products, bundles, promotions, and privacy choices.

Step 8 added observability, abuse controls, CSP, security verification, accessibility, performance budgets, backup/restore drills, and incident response.

This is the final roadmap step.

It may prepare, provision, deploy, verify, and—only after explicit owner approval—enable production charging and perform one real low-value purchase/refund test.

Never spend money, purchase a provider plan, modify registrar/DNS records, create or rotate production credentials, email a real recipient, charge a real payment method, refund a real charge, or expose a public production service without explicit owner authorization.

When access or authorization is missing, complete all reversible preparation and stop at the documented gate.

NON-NEGOTIABLE RELEASE RULES

1. Never place production secret values in source code, commits, patches, terminal output, screenshots, logs, documentation, chat, issue trackers, build artifacts, or the final response.

2. Refer to secrets only by variable name, owner, scope, version, and verified presence.

3. Development, preview/staging, and production must use separate Supabase projects, Stripe environments, Resend configurations, credentials, domains, data, and email-recipient policies.

4. Preview deployments must never receive live Stripe keys, production Supabase service credentials, production buyer data, or unrestricted production email access.

5. Do not copy production personal or order data into preview or development.

6. Production database setup uses forward migrations only.

7. Never run `supabase db reset`, destructive seed scripts, fixture truncation, or local test commands against production.

8. Every production command must verify the intended target project and environment before execution.

9. Database and application changes must remain backward and forward compatible across the rollback window.

10. A Vercel rollback does not roll back Supabase schema or data, Stripe or Resend events, emails already sent, signed URLs already issued, or charges already completed.

11. Live charging remains disabled until the complete release checklist is green and the owner explicitly approves activation.

12. The presence of a live Stripe key must not automatically enable charging.

13. The success page, browser, admin interface, deployment process, or test script can never mark an order paid or grant fulfillment.

14. Only verified or reconciled Stripe payment state may authorize fulfillment.

15. The real smoke test must use an approved, rights-cleared, low-value product, payment method, market, and inbox.

16. Preserve the resulting financial and audit records.

17. Refund through Stripe and verify webhook-driven access revocation.

18. Never delete or modify the real test order merely to make production appear clean.

19. Never test a live chargeback, stolen card, arbitrary customer email, destructive restore, or production load test.

20. Dangerous, delayed, declined, dispute, malformed, and replay scenarios remain in Stripe sandbox or isolated environments.

21. DNS, TLS, email authentication, merchant identity, tax, supported markets, licensing, legal content, privacy, accessibility exceptions, monitoring ownership, backup readiness, and incident contacts are mandatory release gates.

22. Prefer a staged production deployment and manual domain promotion.

23. Keep a known-good application deployment and a schema-aware rollback or forward-fix procedure.

24. If a critical gate fails, keep charging disabled, preserve evidence, and report the exact owner action required.
