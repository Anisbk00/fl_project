     4→
     5→1. Product vision and non-negotiable requirements
     6→
     7→Build a worldwide digital-product store for music producers, inspired by the useful parts of FLPStudio.com's business model but not copied visually or technically.
     8→
     9→The store will sell only content that the owner has the legal right to distribute, including:
    10→
    11→original DAW project files and educational remakes;
    12→
    13→original stems rendered by the owner;
    14→
    15→original WAV/sample packs comparable in format and usefulness to well-known producer packs, but containing no copied third-party audio, branding, artwork, or files;
    16→
    17→optional free products used as acquisition products.
    18→
    19→Core user requirements:
    20→
    21→Public storefront with no customer registration or customer login.
    22→
    23→Guest cart and guest checkout.
    24→
    25→Only the owner/admin can sign in.
    26→
    27→Admin can create, edit, archive, publish, and organize products and upload assets.
    28→
    29→Every product can have an audio preview and optional video preview.
    30→
    31→Every product page exposes useful technical information: product type, DAW and version, BPM, musical key, duration, included formats/files, total download size, required plugins and versions, genre, license summary, and update date.
    32→
    33→Payments use Stripe-hosted Checkout, with eligible major payment methods and wallets managed dynamically in Stripe. The application never handles card details.
    34→
    35→Paid deliverables are private and are never exposed by permanent public URLs.
    36→
    37→Supabase is the database, authentication, and object-storage platform.
    38→
    39→Vercel is the deployment platform.
    40→
    41→The finished product must be secure, fast, accessible, SEO-ready, observable, tested, and release-ready.
    42→
    43→2. Lessons carried forward from the FLP Studio audit
    44→
    45→The new product must deliberately improve on the weaknesses found in the reference store:
    46→
    47→Do not allow broken home-page redirects or dead collection links.
    48→
    49→Make a large catalog discoverable with filters for genre, BPM, musical key, DAW/version, plugins, product type, price, and recency.
    50→
    51→Use clean product names and readable cards; never truncate the only useful identifying information.
    52→
    53→Display compatibility information before purchase.
    54→
    55→Add verified-buyer reviews later; never fabricate reviews or structured review data.
    56→
    57→Use one semantic H1 per page and valid Product, Offer, BreadcrumbList, and eligible Review structured data.
    58→
    59→Avoid keyword stuffing and auto-generated low-quality product copy.
    60→
    61→Render money accessibly and consistently from integer minor units.
    62→
    63→Keep refund, license, privacy, consumer-rights, and download policies consistent.
    64→
    65→Clearly state independence from DAW vendors and referenced artists whenever legally appropriate.
    66→
    67→Add measurement for search, preview play, add-to-cart, checkout start, purchase, and download without leaking sensitive data.
    68→
    69→Prefer improving discovery and trust over blindly adding thousands of products.

    71→3. Architecture decisions
    72→
    73→Application
    74→
    75→Next.js 16 App Router, latest stable 16.x release at implementation time; no canary or beta framework packages.
    76→
    77→React and TypeScript versions selected by the stable Next.js release.
    78→
    79→Node.js 24.x, pinned in package.json and local tooling because it is Vercel's current default LTS runtime.
    80→
    81→pnpm with a committed lockfile and pinned package-manager version.
    82→
    83→TypeScript strict mode, including noUncheckedIndexedAccess.
    84→
    85→Tailwind CSS and shadcn/ui for the later visual-system phase; install only what Step 1 actually uses.
    86→
    87→Server Components by default. Client Components only for interactivity such as the audio player, filters, cart, and admin upload progress.
    88→
    89→No custom Express server. Use Server Actions for authenticated mutations and Route Handlers for webhooks, checkout creation, downloads, and other true HTTP endpoints.
    90→
    91→Every Server Action and Route Handler performs its own authentication, authorization, input validation, and rate-limit check where applicable. A protected layout or Next.js Proxy is never treated as the only authorization layer.
    92→
    93→Supabase
    94→
    95→Postgres is the source of truth for catalog metadata, orders, fulfillment state, and download grants.
    96→
    97→Supabase Auth is used only for manually provisioned admin accounts. Public self-sign-up is disabled.
    98→
    99→Admin authorization is based on the authenticated Supabase user ID appearing in a private admin allow-list, not merely an email supplied by the browser.
   100→
   101→Require TOTP MFA/AAL2 for admin access before production launch.
   102→
   103→Use current sb_publishable_... and sb_secret_... API keys. Do not build a new project around the legacy anon or service_role keys.
   104→
   105→The publishable key may be used in the browser because RLS is the real access boundary.
   106→
   107→The secret key is imported only from server-only modules and never appears in a client bundle, log, URL, repository, or public document.
   108→
   109→Enable RLS and explicit grants on every table in an exposed schema. Test allow and deny cases with pgTAP/Supabase database tests.
   110→
   111→Public visitors can read only published, rights-cleared catalog data and its explicitly public media.
   112→
   113→Public previews and cover images live in an intentionally public bucket for CDN delivery.
   114→
   115→Purchased archives/project files live in a private bucket. Later, a server-side fulfillment check will issue short-lived signed download URLs.
   116→
   117→Large admin uploads go directly from the authenticated admin browser to Supabase Storage using TUS/resumable uploads or signed upload tokens. Never proxy large ZIP/WAV/project files through Vercel Functions.
   118→
   119→Use immutable/versioned storage paths rather than overwriting the same CDN path.
   120→
   121→Payments and fulfillment — later phase
   122→
   123→Stripe-hosted Checkout, guest checkout, one-time payments.
   124→
   125→The server recalculates every line item from trusted database values; it never accepts price or entitlement data from the browser.
   126→
   127→Let Stripe dynamically present eligible payment methods configured for the merchant, currency, amount, and customer location. Do not promise that every method is available in every country.
   128→
   129→Stripe webhooks are the payment authority. The success page is for user experience, not proof of payment.
   130→
   131→Verify Stripe signatures against the raw request body.
   132→
   133→Make fulfillment idempotent and concurrency-safe using unique Stripe event/session/payment identifiers and database transactions.
   134→
   135→Handle both immediate success and delayed payment events before granting files.
   136→
   137→Use Stripe Tax or another reviewed tax solution only after merchant country, legal entity, and tax obligations are confirmed.
   138→
   139→Guest delivery — later phase
   140→
   141→Collect the customer's delivery email through Stripe Checkout.
   142→
   143→After verified payment, create an order, immutable order-item snapshots, and download grants.
   144→
   145→Email a high-entropy access link. Store only a cryptographic hash of the access token in the database.
   146→
   147→Validate token status, order payment status, expiry, revocation, and download limits before issuing a short-lived Supabase signed URL.
   148→
   149→Do not expose storage object paths in public catalog APIs.
   150→
   151→Be honest that signed links reduce casual unauthorized sharing but cannot provide perfect DRM after a customer downloads a file.
   152→
   153→Performance
   154→
   155→Render public catalog/product content on the server and cache/revalidate deliberately.
   156→
   157→Keep admin and order pages dynamic and uncached.
   158→
   159→Use optimized images, compressed preview audio, lazy loading, and small client bundles.
   160→
   161→Use URL search parameters for shareable catalog filters.
   162→
   163→Add indexes that match real catalog queries; confirm with query plans instead of guessing.
   164→
   165→Place Vercel Functions near the selected Supabase project region.
   166→
   167→Define measurable launch budgets later for Core Web Vitals, JavaScript weight, images, and audio.
   168→
   169→Security model
   170→
   171→Defend specifically against:
   172→
   173→unauthorized admin access and privilege escalation;
   174→
   175→public reads of drafts or private deliverables;
   176→
   177→secret-key exposure;
   178→
   179→price/cart manipulation;
   180→
   181→forged or replayed payment webhooks;
   182→
   183→duplicate fulfillment;
   184→
   185→guessing, replaying, or sharing download links;
   186→
   187→XSS through product descriptions and metadata;
   188→
   189→malicious or invalid uploads;
   190→
   191→abusive checkout/download/API traffic;
   192→
   193→sensitive customer/payment data appearing in logs;
   194→
   195→dependency and supply-chain vulnerabilities.
   196→
   197→Important controls include admin MFA, server-side authorization, RLS and grants, private storage, signed URLs, input schemas, sanitization, safe Markdown rather than arbitrary HTML, file allow-lists and size limits, checksums, rate limits, CSP/security headers, idempotency constraints, minimal data retention, dependency updates, audit logs, and tested backups.

   237→5. Legal and operational release gate
   238→
   239→The store must not publish or sell:
   240→
   241→stems extracted from commercial masters;
   242→
   243→third-party sample-pack files, presets, MIDI, artwork, or project assets without redistribution rights;
   244→
   245→a famous song remake merely because it was recreated by ear, unless the composition, included audio/assets, naming, artwork, and intended distribution have been reviewed and cleared as required;
   246→
   247→product copy or branding that implies endorsement by an artist, label, DAW vendor, or sample-pack creator.
   248→
   249→The database therefore includes a rights status and prevents publication until a product is marked original or licensed. This is an engineering guardrail, not a substitute for legal advice. Before accepting live orders, verify business-registration, payment-processor eligibility, tax/VAT, consumer-contract, privacy, copyright, trademark, licensing, refund, and digital-withdrawal requirements for the actual operating jurisdiction and target markets.
